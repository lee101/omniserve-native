# O1 optimization round (2026-10-23)

Branch `llm-optim-20261023` (worktree `omniserve-native-optim`). Live on prod as
`deploy-prod-20261023-o1c` through the drop-in
`/etc/systemd/system/omniserve-native.service.d/zzzzzzzzzzz-o1-20261023.conf`
(repo copy: `systemd/omniserve-native-o1.conf`).

Rollback: delete that drop-in, `systemctl daemon-reload`, restart. The service then
falls back to `deploy-prod-20261022-mtp`. To turn off only the image yield at runtime:
`curl -XPOST localhost:8791/admin/sd/yield -H 'X-Omniserve-Internal: local' -d 0`.

## Profile (nsys, local 3090 Ti, gemma-4-E4B Q8_0 + MTP draft 2, 1 stream)

- The GPU was busy 72% of the time at 1 stream and 71% at 8 streams. The gaps were
  host work on the critical path:
  - Sampling.
  - The MTP draft chain: two decodes in a row, each with its own input upload,
    launch and sync.
  - About 25 small synchronous `ggml_backend_tensor_set` uploads per graph (masks
    of 1 MB and 256 KB, tokens, positions, embd rows).
- Per MTP draft, llama.cpp copied the full 1 MB logits row to the host even though
  the token was sampled on the device. The greedy backend sampler leaves
  `data->logits` set, so `t_sampled_logits` is copied back.
- Target decode, 3 rows: 9.5 ms of kernels with no gaps between them (CUDA graph).
  - `mul_mat_vec_q` took 6.4 ms, about 670 GB/s.
  - The rest is about 1500 small kernels, mostly `rms_norm` (302 calls × 4 µs),
    `quantize_q8_1`, flash attention, and q8_0 KV dequantization.
  - Fixing these needs kernel changes. Changing the reduction order would break
    bit-identical greedy output, so I left them alone.
- On the host, `gather_top` (the exact top-(k + window) cut over 262k logits)
  dominates sampling: 90–250 µs per row on the Ryzen and 330–480 µs on the prod
  Broadwell. The sampler chain after it costs only 20–40 µs.
- On prod the dominant GPU load is the background image job: about 550 images per
  hour, so roughly 67% of GPU time. Chat traffic is small (about 2.3k engine steps
  a day). Chat decode slows by 1.5–2× while a DiT step runs at the same time.

## Changes

1. **Image yields to live chat** (`OMNISERVE_NATIVE_SD_YIELD_LLM_MS`, 2000 on prod;
   `POST /admin/sd/yield` changes it at runtime).
   - How it pauses:
     - A background-tier image pauses while the LLM engine has live sequences.
     - It pauses between denoising steps, using sd.cpp's progress callback.
     - It also pauses inside a step, after each flash-attention node. This uses
       sd.cpp's eval callback, which splits the graph there. No ggml-cuda fusion
       crosses an attention output.
   - Each image may pause for at most the budget in total.
   - The eval callback is installed only while the current image has a budget. A
     split happens only when the LLM is live.
   - Images are byte-identical with the yield off or armed (prod md5 check, seeds
     4242 and 4243).
   - The `[image]` log line gains `y=<ms paused>`.
2. **Device conf-greedy MTP sampler.**
   - It does device argmax plus the argmax's softmax probability, and drops the
     logits view. That removes the 1 MB D2H copy per draft.
   - Drafts are unchanged, so the output is identical.
   - Its confidence also drives the optional DSpark-style draft gating (item 5).
3. **AVX2 `collect_ge` in `gather_top`.** Same candidate set in the same order, and
   1.5–1.9× faster in the microbenchmark.
4. **Same-tier FIFO for VRAM lease waits, plus a log line for each image lease
   denial.**
   - Before this, a caller that loops request after request could take every
     released lease ahead of a queued waiter of the same tier.
   - In the old process's access log, image requests failed with 503 every 20 s
     during 2026-10-22 18:30–21:30 (zero successful images in hours 18–20) and
     2026-10-23 01:20–02:00. Each 503 was a 20 s `VRAM_WAIT_MS_BACKGROUND` timeout.
   - Root cause not proven: the journal from that period is gone. FIFO is the
     likely fix, and the new log line will show the device numbers if it happens
     again.
5. **Opt-in, measured and left off:**
   - `OMNISERVE_NATIVE_LLM_MTP_CONF=<min cumulative p>` stops drafting once the
     product of the head's probabilities falls below the threshold. It pads the
     verify rows and dummies the MTP rows so graphs keep their shape.
   - `OMNISERVE_NATIVE_LLM_PAR_GATHER=1` gathers each verify row on the sampler
     pool.
6. **Trace additions.** Per-row gather and chain time, and MTP confidence
   calibration bins (accepted/drafted by head probability decile, per draft
   position).

## Prod results (RTX 5090, live image job running, `X-Omniserve-Internal: local`)

I alternated yield 0 and yield 2000 (or 3000) every 30–40 requests, waiting for one
image to finish after each switch.

| | yield 0 | yield 2000 |
| --- | ---: | ---: |
| 1 stream, per-stream tok/s (3 reps) | 123 / 150 / 109 (mean 127) | 160 / 154 / 157 (mean 157, +24%) |
| 1 stream, aggregate tok/s | 115 / 117 / 106 | 136 / 129 / 133 (+17%) |
| 1 stream, TTFT p50 / p95 ms | 37 / 66 | 27 / 57 |
| 2 streams, aggregate tok/s | 150 / 151 / 161 | 159 / 161 / 167 (+5%) |
| 2 streams, TTFT p50 ms | 384 / 242 / 316 | 62 / 58 / 71 |

- An earlier run with a 3000 ms budget gave 126 → 153 tok/s at 1 stream.
- Steady decode dropped from 10.8–11.8 ms to 7.4–9.1 ms per step while images were
  queued.
- Image cost:
  - Under continuous synthetic chat load, every overlapping image is delayed by
    the full budget (+2 s).
  - At prod's real chat volume (about 2.3k engine steps a day, mostly short
    replies), the total pause is bounded by chat time. That is under about 1% of
    image GPU time.
  - Watch `y=` in the `[image]` lines.
- 1/8/32-stream bench before and after the binary swap (yield off, so this measures
  the exact changes only):
  - 160–170 / 473–490 / 436–522 tok/s, unchanged within the noise of the shared GPU.
  - The engine trace shows host sampling at 0.53–0.61 ms per step, against
    0.43–1.05 ms before.

## Measured and rejected

- **Confidence-gated MTP draft length** (DeepInfer `MTPVarlen`-style: cumulative
  product of the head's own probabilities, draft cap 3–6, threshold 0.15–0.35).
  - The head's probability is well calibrated: decile 9 is accepted 86–90% of the
    time, decile 1 about 10%.
  - But on this model and card, verify rows beyond 2 and the extra MTP calls cost
    about what they save.
  - Without padding, variable shapes caused llama.cpp graph rebuilds and CUDA graph
    recaptures, which made it worse. Padded, it was neutral (145–154 vs 152–156
    tok/s, noisy).
  - The prod finetune accepts 0.36 per draft, so the possible gain there is smaller
    still.
- **Parallel per-row gathers on the sampler pool:** waking the pool cost more than
  the scan it saved (local sample time 0.34–0.40 vs 0.27–0.38 ms per step).
- **WebP `method` 2:** 2.2× faster encode, but −0.26 dB PSNR. That is a quality
  change. `thread_level=1` gives the same bytes but only −4%.
- **GPU top-k prefilter:** CUDA 12.9 has no CUB DeviceTopK, so `ggml_top_k` falls
  back to a full argsort.

## Open items

- **LoRA reload.**
  - Images alternate between LoRA and no-LoRA requests. Each return to the LoRA
    reloads `the_look` from the file: about 290 ms, on 27% of images (4740 vs
    4447 ms median).
  - Parking the adapter in VRAM would cost about 340 MB of idle VRAM, which risks
    background-tier 503s.
  - A host-side cache of the converted F32 factors would avoid that, but needs an
    sd.cpp rebuild.
- **Synchronous uploads.** About 25 per graph, roughly 0.25 ms per graph on prod
  with 3 graphs per step. Fixing it needs an event-based `set_tensor` patch in the
  private llama.cpp.
- **Graph rebuilds.** About 7% of prod steps are "reshaped" (llama.cpp graph
  rebuild, +9 ms on the Broadwell). A multi-entry graph cache in llama.cpp would
  remove this.
- **Sampling scan.** `gather_top` scans 1 MB per row at about 350 µs on the
  Broadwell. Device-side compaction of the candidates would remove the PCIe copy
  and the scan.
