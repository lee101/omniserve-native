# MTP speculation in the batched LLM engine (2026-10-22)

Opt-in: `OMNISERVE_NATIVE_LLM_MTP=/path/mtp-gemma-4-E4B-it-Q8_0.gguf`, with
`LLM_MTP_DRAFT` (2, max 8) draft tokens and `LLM_MTP_MAX_ACTIVE` (4): drafting
only runs while at most that many sequences are live. `LLM_MTP_BACKEND_SAMPLE=0`
drafts with a host argmax instead of on the device. Unset, the engine is
unchanged (no nextn staging, same batch size).

## How

- One `LLAMA_CONTEXT_TYPE_MTP` context on the head, `ctx_other` = the batched
  target. Gemma-4's assistant reads the target's KV (shared cells, no writes),
  so there is no catch-up decode and nothing to roll back on the draft side.
- The target stages the post-norm hidden row for every output row (masked
  nextn: logits rows only, ~10 KB per row).
- Per step, after building the batch: for each decode row whose hidden row is
  from the previous target decode, draft greedily, one MTP decode per draft
  position for all sequences at once (all drafts at the position of `next`, as
  the Gemma-4 assistant expects). Greedy sampling runs on the device (llama.cpp
  backend sampler), so no logits row crosses PCIe. The drafts are spliced in
  behind their sequence's row, ahead of the prefill, so verify rows stay
  contiguous and in the first ubatch.
- Verify: the sequence's own sampler chain (penalties, DRY, top-k/p, temp,
  dist) samples row 0, accepts it into its history, and continues to row i+1
  only if it sampled draft i itself; EOG stops the run. Same calls in the same
  order as sequential decoding, so the output distribution (and the seeded RNG
  stream) is unchanged. Rejected rows leave the KV (`llama_memory_seq_rm`).
- Draft count per sequence is capped by `max_new - produced - 1` and ring room,
  so `max_tokens` is exact and the ring never overflows. Stop strings,
  cancellation, prefix forks/reuse, eviction and preemption are untouched
  (a failed step drops the drafts; the hidden row is then stale and the next
  step decodes plainly).
- llama.cpp unchanged: the nextn staging calls are resolved by mangled name, as
  the per-slot MTP path already did.

## Exactness

- CPU (kernels are batch-width invariant there), temperature 0, 8 prompts x 80
  tokens, sequential and with 3 concurrent fillers at temp 0.9 (MTP drafting
  for all live sequences, splicing next to prefill chunks): **byte-identical to
  MTP off in every case** (seq and concurrent; draft 3, device and host
  argmax drafting both checked), with 63-66% of drafts accepted.
  `scripts/llm_batch_parity.py --no-concurrent --limit N` / `--fillers N`.
- GPU, fresh servers, 16 prompts: 11/16 byte-identical to MTP off (mean
  shared prefix 0.84), the same as MTP off against itself under concurrency
  (11/16, 0.80) and MTP off against a second MTP-off server with a different
  request history (9/16). A row's logits depend in their last bits on the
  batch width it was decoded in (FA kernel choice, matmul tiling), and greedy
  near-ties flip; same effect as `quality.md` and the batching doc record.
  Task accuracy equal (8/12).

## Throughput (RTX 3090 Ti, gemma-4-E4B-it Q8_0, 32 seqs, KV pool 6)

`scripts/llm_throughput_bench.py`, roleplay persona, 200 tokens, temp 0.8,
`X-Omniserve-Internal: local`. Servers run side by side and are interleaved per
level, 3 reps. Another session ran GPU jobs during reps 2-3 (off single-stream
fell from 103 to 94); rep 1 was quiet. Median of 3 (rep 1 in brackets):

- Single stream +35-40%, 2 streams +25-30% aggregate and per stream.
- Acceptance per draft token on roleplay at temp 0.8: draft 1 0.56, draft 2
  0.40-0.44, draft 3 0.30-0.34 (draft 2 and 3 equal at 1 stream, draft 2 ahead
  from 4 up). On the parity prompts at temp 0: 0.66-0.69 (draft 2).
- With drafting on for every sequence (k=32) it still gains to 16 streams on
  this card, but costs 10% at 32 and doubles TTFT; k=4 matches off from 8 up.
- TTFT: unchanged alone (24-25 ms both, probe), +6-13 ms at 2-4 streams (a new prompt waits for one
  draft round and joins a wider step). Measured with a persistent background
  stream: off 26-28 ms, MTP 32-35 ms p50.
- Engine trace at 1 stream: verify step 10.6 ms vs 9.1-9.7 ms plain; drafting
  1.8 ms per step for 2 drafts (0.9 ms per MTP decode, about half of it CPU
  graph build). Host argmax over the 262k logits instead of device greedy cost
  1.5 ms per draft decode.

## Caveats

- Prod serves `gemma-roleplay-v2-q8_0`, a finetune of gemma-4-E4B; the head is
  the base model's. Acceptance on the finetune is unmeasured (its file is not
  on this host) and may be lower; check `/status.speculation.acceptance`.
- Prod's host is a 2016 Broadwell on PCIe 3.0; the draft round is partly CPU
  (graph build, launches), so expect a smaller gain there than here.
- VRAM: +~200 MiB at startup (head 94 MiB, draft compute buffer, larger target batch).
- The admin swap path keeps using `OMNISERVE_NATIVE_LLM_MTP`; a head that does
  not match the new model's width/vocab is refused and MTP stays off.
